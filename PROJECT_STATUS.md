## Текущая цель

Подготовить реализованный React/Vite-сайт и Strapi CMS к production-развёртыванию без потери каталога, заявок, документов и почтовых уведомлений. Ближайший фокус — обеспечить серверную достоверность состава и стоимости заявки, закрыть автоматизированные проверки backend и затем провести staging/production-проверку.

## Что завершено

- Реализована адаптивная витрина на React 19, TypeScript и Vite 8: главная страница, каталог, фильтры, карточка товара, производственные и логистические разделы, контакты.
- Каталог из 16 позиций извлекается из `data/Труба_гофрированная_характеристики_.xlsx` в одинаковые seed-файлы для frontend и CMS.
- Подключена Strapi 5 CMS с типами контента «Товар» и «Заявка». Пустая локальная база автоматически заполняется товарами; публичной роли разрешены только чтение товаров и создание заявки.
- Реализован выбор товаров с количеством бухт, сохранением выбора в `localStorage`, предварительным расчётом суммы и передачей состава в форму.
- Форма заявки имеет клиентскую и серверную валидацию, явное согласие на обработку данных, состояния отправки/ошибки/успеха и не теряет введённые данные при ошибке.
- Добавлены отдельные страницы `/privacy`, `/terms`, `/consent`; версия согласия и время принятия сохраняются в заявке.
- Сертификаты и информационное письмо открываются внутри сайта в модальной карусели; доступны оригинальные PDF.
- После сохранения заявки CMS отправляет уведомление менеджеру через SMTP. Сохраняются закрытые от публичного API поля статуса отправки, времени и идентификатора сообщения. При сбое SMTP заявка остаётся в CMS.
- Добавлены светлая визуальная система, адаптивные состояния, анимации с учётом `prefers-reduced-motion`, клавиатурное управление модальными окнами и защита от горизонтального переполнения.

## Ключевые технические решения

- `web` и `cms` развиваются как два приложения в одном каталоге; общие команды находятся в корневом `package.json`.
- Источник каталога для сайта — публичный Strapi API. Если CMS недоступна или вернула пустой каталог, frontend молча использует `web/src/data/products.json`.
- Seed CMS выполняется только при пустом каталоге и не перезаписывает товары, уже заведённые через Content Manager.
- Локально используется SQLite (`cms/.tmp/data.db`). Конфигурация допускает PostgreSQL/MySQL через переменные окружения, но production-база и миграция данных ещё не выполнены.
- В браузере сохраняются только SKU и количество. Контактные данные в `localStorage` не сохраняются.
- Заявка сначала записывается в CMS, затем выполняется SMTP-отправка. Ошибка почты не превращает уже сохранённую заявку в ошибку формы и не провоцирует повторную отправку клиентом.
- SMTP-секреты находятся только в исключённом из Git `cms/.env`; публичный пример не содержит пароля. Значения секретов в этом документе не фиксируются.
- Все известные URL, включая правовые, теперь имеют отдельные HTML в сборке. Production-сервер должен отдавать соответствующий файл по чистому адресу и настоящий HTTP 404 для неизвестных URL; глобальный SPA fallback на главную не используется.

## Известные проблемы и ограничения

1. **Нет Git-истории.** В корне и вложенных приложениях отсутствует `.git`; `git status` и diff недоступны. Нельзя подтвердить происхождение файлов, список незакоммиченных изменений и точку отката.
2. **Товарные данные заявки не являются доверенными.** `cms/src/api/lead/controllers/lead.ts` проверяет SKU и количество, но сохраняет переданные браузером название, длину бухты и цену. Итог и текст письма можно исказить изменённым запросом. Сервер должен загружать актуальные товары по SKU и сам формировать снимок заявки и сумму.
3. **Fallback каталога скрывает проблемы CMS.** При любой ошибке или пустом ответе сайт без индикации показывает встроенный seed. Пользователь может увидеть устаревшие цены, а мониторинг не узнает об отказе API.
4. **Нет автоматического повтора SMTP.** Неуспешные уведомления получают статус «Ошибка отправки» и требуют ручной обработки в CMS. Очередь, retry/backoff и служебное оповещение отсутствуют.
5. **Корневые CMS smoke-команды сломаны.** `npm run cms:smoke:add` и `npm run cms:smoke:cleanup` запускают Node из корня; Strapi не находит `cms/config`, и сценарий падает с ошибкой конфигурации БД. Рабочий временный запуск указан ниже.
6. **Production-инфраструктура не готова и не проверена.** Нет подтверждённых PostgreSQL, постоянного хранилища uploads, резервного копирования/восстановления, ограничений CORS, rate limit/anti-spam для публичной формы, мониторинга и staging-проверки.
7. **Правовые тексты требуют подтверждения владельцем.** Нужно сверить реквизиты, сроки хранения и фактический процесс обработки/удаления данных до публикации.
8. **Публичный сайт не проверен на соответствие этой сборке.** Локальные build, QA и SMTP-проверка не доказывают, что изменения развёрнуты на `rusplast-zavod.ru`.

## Уже опробованные, но неработающие способы

- Не запускать CMS smoke через `npm run cms:smoke:add` из корня до исправления скрипта. Временный рабочий вариант: `cd cms && node scripts/cms-smoke.cjs`; после проверки обязательно `node scripts/cms-smoke.cjs --cleanup`.
- Для визуального QA недостаточно запуска `npm run dev:web -- --host 127.0.0.1`: в текущем корневом npm-скрипте аргумент разбирается некорректно, и QA может получить `ERR_CONNECTION_REFUSED` на `127.0.0.1:5173`. Рабочий запуск: `npm --prefix web run dev -- --host 127.0.0.1`.
- Не использовать успешный frontend fallback как доказательство работы CMS: визуально сайт остаётся доступным даже при отказе API.

## Следующие шаги

1. Восстановить Git-контекст: получить исходный репозиторий с историей либо инициализировать новый только после согласования базовой версии; зафиксировать текущий снимок без `cms/.env`, SQLite и build-артефактов.
2. Изменить создание заявки: принимать от клиента только SKU и количество, получать опубликованные товары из CMS, отклонять неизвестные SKU, сохранять серверный снимок характеристик/цен и рассчитывать сумму на сервере.
3. Добавить backend-тесты для валидации заявки, подмены цены, неизвестного SKU, пустой консультационной заявки, SMTP success/failure и приватности служебных полей.
4. Исправить корневые smoke-команды так, чтобы Strapi всегда запускался с рабочей директорией `cms`; включить build, lint, backend tests, smoke и visual QA в единый повторяемый pre-release сценарий.
5. Определить политику отказа CMS: показывать состояние «каталог временно недоступен» либо явно маркировать и контролировать seed fallback; добавить логирование/мониторинг ошибок API.
6. Добавить надёжную доставку уведомлений: очередь или ограниченные retry с backoff, ручный повтор из CMS и оповещение менеджера о накопившихся ошибках без раскрытия персональных данных в логах.
7. Подготовить production: PostgreSQL, постоянные uploads, секреты в окружении сервера, CORS allowlist, rate limit/anti-spam, TLS, backup/restore и маршрутизацию отдельных HTML с корректным HTTP 404.
8. Согласовать правовые документы и актуальность опубликованных сертификатов с владельцем данных.
9. Развернуть staging и повторить полный E2E: загрузка каталога именно из CMS, создание заявки, сохранение серверных цен, SMTP и фактическое получение письма, мобильный/desktop QA и прямое открытие правовых URL.
10. После резервной копии развернуть production и отдельно проверить публичный релиз, API, формы, доставку писем, логи и восстановление после сбоя.
